Source deep dive — the search KPI tables

Findings from the 2026-08-19 investigation into how OLX's search KPI pipeline is built, why Uzbekistan was missing from it, and how the UZ numbers on this dashboard were reconstructed. The four original Tableau queries are at the bottom, exactly as written. Reference: Scripts/uz_search_kpis/ (README.md + TABLES.md, vendored into this repo under sql/search/tableau/).

The gap: UZ was missing, but only from the finished table

  • The production weekly table odyn_search_and_ad_ranking.weekly_search_kpis_tableau — the one the search KPI dashboards are built on — contains only BG, PL, PT, RO and UA. No Uzbekistan.
  • Its daily precursors however (daily_search_users_kpis + daily_search_volume_kpis) do contain Uzbekistan and Kazakhstan, with full history from 2024-12-28 — the UZ data existed all along, it just never got rolled up.
  • So we built an exact 29-column replica of the production weekly table for UZ from those daily tables (1_weekly_search_kpis.sql below) — a drop-in Tableau replacement.
  • Validated cell-perfect against production for Poland: 2 weeks × 15 rows × 24 metrics, every value matched. That is what makes the replica trustworthy — the same query run against a country the production table does cover reproduces it exactly.

Reverse-engineered semantics (why the numbers look the way they do)

  • users_* / volume_* are average daily values — floor(sum ÷ days_in_week) — not weekly totals and not distinct users over the week. This is the single most misread property of the whole dataset, and the reason every averaged chart on this dashboard says so in its title.
  • ssu_* and avg_*_su are unweighted averages of the daily ratios, rounded to 5 dp — not period ratios.
  • funnel_stage_adview_pct = ssu_adview; funnel_stage_reply_pct = ssu_lead. The funnel columns are just the conversion ratios under another name.
  • funnel_stage_method_share_of_search = ratio of the floored weekly user counts (method ÷ All), NULL on search_method = 'All' rows; funnel_stage_search_pct / _platform_pct = 1.0 on the All rows, NULL otherwise.
  • Week fields are ISO (year_of_week() / week()), weeks start Monday, week_label = 'W' || lpad(week, 2, '0').
  • The All rows are deduplicated rollups, not sums of the detail rows — one user can appear under both Keyword and Browsing.

Conventions that bite

  • Country encoding differs by table. daily_search_users_kpis / daily_search_volume_kpis use full names ('Uzbekistan'); daily_user_searches uses ISO codes ('UZ') — and there country is a partition key, so always filter it (it prunes 6/7 of the scan).
  • TGV is not tracked for UZ or KZ — every *_tgv column is legitimately 0, which is why this dashboard drops them entirely rather than charting flat zeros.
  • Category joins go through bi_dim_categories on category_nk + site_sk = 'olx|eu|uz' (923 rows), joined at the deepest available level (L3 → L2 → L1). category_nk = '-1' is Unknown; a NULL after the left join means "no resolvable category".
  • Kazakhstan is available in the same tables ('Kazakhstan' / 'KZ') if this ever needs to cover KZ.
  • These queries aggregate ~600 days per refresh — use Tableau extracts on a schedule, not live connections.

⚠️ Two traps to avoid

  • Do not build on odyn_search_and_ad_ranking.fact_search_events. It looks ideal (one row per listing event with has_adview / has_lead / has_tgv) but contains a single day — 2026-06-01 — for all countries. It is a test snapshot, not a table.
  • Do not roll up daily_user_searches into user counts. Its grain is platform × keyword × category × session, so a session appears in many rows: naive rollups overcount users ~3.5× and searches ~7×. Use the pre-aggregated KPI tables for user counts.

UZ scale check (week of 2026-08-03)

  • ≈ 353K average daily search users
  • ssu_adview ≈ 73% of search users reached an ad view; ssu_lead ≈ 8.4% sent a reply
  • Category split (finance L2, via dim_categories, site_sk = 'olx|eu|uz'): For sale > No category > Motors > Real estate > Jobs > Services

These figures are the sanity baseline: the Search volume and Search users tabs should land in the same neighbourhood, and they do — a useful check after any pipeline change.
